# Architecture

This document describes the V2 system in `project-deliverable-2/`. V1 in `project-deliverable-1/` is preserved for historical comparison and is described where its differences are instructive.

## System overview

The system is a single-user Python CLI run by an event judge on a laptop at a competition. It has three responsibilities: managing a roster of competitors, calculating handicap marks for a heat, and validating that those marks produce fair race outcomes through statistical simulation.

The runtime is a menu loop in `DeliverableTwo.py` that holds session state (`comp_df`, `wood_selection`, `heat_assignment_df`) and routes to handler functions in `ProjectFunctions.py`. All persistence goes through a single Excel workbook, `woodchopping.xlsx`, with three sheets. An optional dependency on Ollama (running locally) provides LLM-based reasoning during prediction and fairness assessment; if Ollama is unavailable the system degrades to a deterministic statistical fallback.

```
+---------------------------------+
|   DeliverableTwo.py             |   menu loop, session state
|   (main loop, 7-option menu)    |
+----------------+----------------+
                 |
                 v
+---------------------------------+
|   ProjectFunctions.py           |   ~30 functions across 5 concerns:
|                                 |   - roster + heat management
|                                 |   - wood selection
|                                 |   - prediction pipeline
|                                 |   - Monte Carlo simulator
|                                 |   - LLM bridge
+----+----------------+-----------+
     |                |
     v                v
+----------+   +-----------------+
| Excel    |   | Ollama (local)  |   network calls limited to localhost
| .xlsx    |   | qwen2.5:7b      |
+----------+   +-----------------+
```

The system runs entirely offline once the Ollama model is pulled. There are no cloud APIs, no auth, no telemetry, no third-party services.

## Data model

The persistence layer is `woodchopping.xlsx`, accessed via `pandas.read_excel` for reads and `openpyxl` for writes. Three sheets:

**`Competitor`** is the roster. Columns: `CompetitorID` (string, e.g. `C001`), `Name`, `Country`, `State/Province`, `Gender`. IDs are generated by `add_competitor_with_times` as `C` followed by a zero-padded row index (`f"C{ws.max_row:03d}"`). The DataFrame is renamed on load to use snake_case columns (`competitor_name`, `competitor_country`, etc.) so internal code never sees the Excel-friendly capitalization.

**`wood`** is the species reference table. Columns include `species`, density, Janka hardness, shear strength, modulus of rupture (MOR), and modulus of elasticity (MOE). The columns have aliases that get normalized in V1's `_load_wood_characteristics_df`. V1 uses these columns to compute a per-species multiplier; V2 uses the species name only, passing the species-specific reasoning to the LLM rather than encoding it numerically.

**`Results`** is the historical times log, append-only in normal use. Columns: `Event` (SB or UH), `CompetitorID`, `Species Code`, `Size (mm)`, `Quality`, `Time (seconds)`, `Heat ID`, `Timestamp`. Loaded by `load_results_df`, which renames columns to snake_case and joins back to `Competitor` on `CompetitorID` to populate a `competitor_name` column for downstream code.

The Excel choice was deliberate. Judges at woodchopping events are not database administrators. They are comfortable opening, editing, and printing spreadsheets. They are not comfortable with `sqlite3 woodchopping.db`. Trading concurrency safety for editability and auditability was the right call for the actual users.

## Access model

There is no authentication and no authorization. The deployment context is one judge running the program on one laptop at one event, sometimes with the laptop borrowed from another judge between events. Anyone with file-system access can edit competitor data, edit wood data, edit results, or view any of it.

This is acceptable because:

1. The data is not sensitive. Competitor times at public events are themselves public.
2. The trust boundary is the laptop, not the program. If an attacker has shell access to the judge's laptop they can do anything. Adding auth to the CLI would not change that.
3. Adding auth would friction the workflow for the actual users. Judges already use spreadsheets without passwords.

The threat model the system *does* need to defend against is accidental data corruption: a judge accidentally typing a string where a number should go, accidentally selecting a competitor twice, accidentally entering a quality rating of 50 instead of 5. Defense is per-input validation in the menu handlers (`enter_wood_quality` clamps to [0, 10]; `select_competitors_for_heat` rejects duplicates; numeric inputs are wrapped in try/except). The strategy is "fail loudly back to the menu" rather than "validate up front, then commit."

The one remote call the system makes is `requests.post` to `OLLAMA_HOST` (default `http://localhost:11434`). This is bounded to a 30-second timeout, falls through to a deterministic fallback on connection error, and never sends competitor data outside the local machine.

## Prediction pipeline

The core innovation in V2 is the prediction pipeline in `predict_competitor_time_with_ai`. Given a competitor name, a wood species, a diameter, a quality rating, and an event code, it produces a tuple `(predicted_time, confidence_level, explanation)`.

The pipeline runs in three stages:

**Stage 1: cascading historical lookup** in `get_competitor_historical_times_flexible`. It first looks for results matching `competitor + species + event`. If fewer than three matches exist, it broadens to `competitor + event` regardless of species. If still empty, the system falls through to the event baseline computed by `get_event_baseline_flexible` (species + diameter + event, then diameter + event, then event-wide). At each fallback step the function returns a `data_source` string that is propagated up to the user, so the official sees exactly what data the prediction is based on. This is one of the most important pieces of UX in the system: the judge always knows whether they are looking at "Smith on Tasmanian Bluegum from 4 races" or "all competitors on any 350mm Underhand block from the last two seasons."

**Stage 2: median + LLM quality adjustment**. Once a base time is established, the LLM is given a structured prompt with the historical times, the wood quality rating, and a brief description of the species. It returns a multiplier (e.g. "0.92" for very soft wood that lets a competitor cut faster). The multiplier is bounded; if the LLM returns nonsense, the deterministic fallback uses a piecewise-linear quality curve (1.20 at quality 0, 0.80 at quality 10).

**Stage 3: confidence labeling**. Each prediction carries a confidence string (`high`, `medium`, `low`) derived from the data source breadth. Exact-match predictions are `high`; competitor + event fallbacks are `medium`; event-baseline fallbacks are `low`. These labels are nominal, not calibrated against ground truth. This is documented honestly in the failure-modes section below.

The output of the pipeline is then fed into `calculate_ai_enhanced_handicaps`, which sorts competitors slowest-to-fastest and applies the AAA rule: slowest gets a mark of 3 seconds, everyone else gets `3 + ceil(slowest_time - their_time)` clamped to [3, 180].

## Validation pipeline

`run_monte_carlo_simulation` is the fairness check. Given a list of competitors and their assigned marks, it simulates 250,000 races and reports per-competitor win rate, average finish position, and finish-time spread.

Each simulated race in `simulate_single_race` does the following: for each competitor, sample a performance-noise term from a uniform distribution `[-3, +3]` seconds, add it to the predicted time, subtract the handicap mark, sort competitors by adjusted finish time. Lowest is the winner.

The critical design choice is *absolute* variance (every competitor's noise is sampled from the same `[-3, +3]` range) rather than *proportional* variance (e.g. ±10% of each competitor's predicted time). This was discovered by testing both. Proportional variance gave a faster competitor a much narrower outcome distribution in absolute seconds, which combined with the integer ceiling in the mark calculation produced systematically biased races, a 31% to 6.7% win-rate spread in the worst test case. Absolute variance produced near-equal win probability and reflects how real-world performance noise actually behaves: technique inconsistency, wood grain variation, and equipment slip are roughly constant in seconds, not in percent.

After simulation, `get_ai_assessment_of_handicaps` sends the win-rate distribution to the LLM and asks for a fairness rating (`Excellent` / `Very Good` / `Good` / `Fair` / `Poor` / `Unacceptable`). A deterministic fallback computes the same rating from the spread-of-win-rates if the LLM is unavailable.

## Production posture

This CLI is "production" in the sense that it is intended to run on a judge's laptop at an actual tournament. Production posture is therefore:

- **No network dependencies** beyond `localhost:11434`. The program runs on a tournament Wi-Fi (or no Wi-Fi). Ollama is local; Excel is local.
- **Graceful LLM degradation**. Every LLM call has a fallback path (`call_ollama` returns `None` on connection error; downstream code branches to a deterministic computation). The judge can run the program without Ollama at all and lose only the LLM-flavored quality reasoning and fairness narrative; the math still works.
- **Single-step writes**. Heat results are appended to the Excel `Results` sheet via `openpyxl` `append + save`. There is no transaction; partial writes are not handled. Mitigation is that the user is prompted to confirm before saving and the save is the last step.
- **Error containment**. Every user-input handler catches exceptions and returns to its parent menu. No traceback should ever reach the user during normal use.
- **No CI, no tests, no logging**. This is the largest production gap and is called out in failure modes below.

## Failure modes and what I would do differently

These are the honest gaps. Each is a real risk in the deployed context.

**1. Excel concurrency.** If two judges open `woodchopping.xlsx` at the same time, the second writer's changes silently overwrite the first's. There is no file locking. In practice tournaments have one official scorer, but the assumption is brittle. Real fix: move the persistence layer to SQLite, keep the Excel-export functionality as a read-only artifact for printing.

**2. No automated tests.** I tested by hand. The Monte Carlo result distributions were a useful regression check (a broken prediction pipeline produced visibly biased win-rate plots), but there is no `pytest` suite. A prediction pipeline change today could silently break the cascading-fallback ordering and I would not catch it. Real fix: pytest suite covering the deterministic paths in `predict_competitor_time_with_ai`, `compute_marks`, and `simulate_single_race`. The LLM-dependent paths can be tested by injecting a `call_ollama` stub.

**3. LLM confidence scores are nominal.** The `high`/`medium`/`low` labels are based on data-source breadth, not on calibrated prediction error. A competitor with three exact-match races on the same block could still have unpredictable real performance, and the system would call that prediction `high`-confidence. Real fix: hold out the most recent N race per competitor, predict against the held-out times, and bin observed error to produce calibrated confidence.

**4. Magic numbers.** ±3 seconds variance, 180-second cap, 3-second floor, baseline diameter 300mm or 250mm, `temperature=0.3` and `num_predict=50` for the LLM call. These are encoded inline in the functions that use them. Real fix: hoist into a single `config` module so they are inspectable, overridable, and version-controlled as a unit.

**5. No recency weighting.** This is the feedback David Moses Jr. gave me. Older professional competitors whose careers peaked decades ago carry historical times that are no longer representative. The current median computation treats all historical times equally. Real fix: exponential decay weighting on race date, with the half-life as a tunable parameter.

**6. Single event family.** SB and UH are supported; the 3-Board Jigger is not, despite being a common handicap event. The blocker is data sparsity (jigger times are noisier and there is less public data) and rule complexity (jigger has multiple boards, each timed separately). This is a roadmap item, not an architectural defect, but it is the most-requested feature.
